## 1. What went wrong

Both nodes were written against the CUDA namespace and called it unconditionally. Measured on `850986b^`:

| file | `torch.cuda.*` call sites |
| :--- | ---: |
| `nodes/purge_vram.py` | 41 |
| `nodes/memory_manager.py` | 15 |

On an AMD build those calls reach the ROCm runtime, because ROCm publishes itself through `torch.cuda` (`torch.version.hip` set, `torch.version.cuda` `None`). On an Intel build they do not: the device is an XPU, `torch.cuda` has no device behind it, and the allocator calls have nothing to act on. The startup VRAM patch had the same shape: it read NVML, which exists only on NVIDIA.

Reported as [Issue #4](https://github.com/ussoewwin/ComfyUI-DistorchMemoryManager/issues/4).

## 2. Root cause

No backend probe existed. The nodes assumed the device namespace and the memory API from the platform they were written on, so every destructive step was expressed against CUDA regardless of what ComfyUI was actually running on. ComfyUI itself already distinguishes the three cases (`is_intel_xpu()` / `is_amd()` require `cpu_state == GPU`), and `get_torch_device()` tests XPU before falling back to CUDA, but the nodes never consulted those flags.

## 4. The code, verbatim

### 4.1 Backend probes (`nodes/device_backend.py`, 76-107)

```python
def is_xpu():
    """True when ComfyUI runs on an Intel XPU.

    Returns False on this CUDA build by execution, which is the direct evidence
    that the CUDA path is untouched.
    """
    global _XPU_CACHE
    if _XPU_CACHE is not None:
        return _XPU_CACHE
    mm = _comfy_model_management()
    if mm is not None and hasattr(mm, "is_intel_xpu"):
        try:
            value = bool(mm.is_intel_xpu())
        except Exception:
            value = False
        _XPU_CACHE = value
        return value
    if not hasattr(torch, "xpu"):
        return False
    try:
        return bool(torch.xpu.is_available())
    except Exception:
        return False


def xpu_device_count():
    if not is_xpu():
        return 0
    try:
        return int(torch.xpu.device_count())
    except Exception:
        return 0
```

### 4.2 Cache release on every XPU device (176-205)

```python
def xpu_clear_cache_all_devices():
    """Synchronise then empty the XPU allocator on every device.

    Returns the number of devices whose cache was actually emptied. A build that
    cannot synchronise is reported once instead of being counted as success.
    """
    if not is_xpu():
        return 0
    cleared = 0
    sync_failures = 0
    try:
        current = xpu_current_device()
    except Exception:
        current = 0
    for index in range(xpu_device_count()):
        if not xpu_set_device(index):
            continue
        try:
            if not xpu_synchronize():
                sync_failures += 1
            if xpu_empty_cache():
                cleared += 1
        finally:
            xpu_set_device(current)
    if sync_failures:
        print(
            "Backend: XPU synchronize unavailable on %d device(s); "
            "the cache was emptied without waiting for in-flight work" % sync_failures
        )
    return cleared
```

## 5. What it means

- **The CUDA path is unchanged.** `torch.cuda.*` is still called 41 times in `nodes/purge_vram.py` and 15 times in `nodes/memory_manager.py`, exactly as before. The XPU arms are guards placed in front of those blocks, not replacements.
- **AMD keeps the CUDA namespace.** ROCm exposes itself through `torch.cuda`, so the ROCm arm needs no new namespace; it needs only the correct branch decision.
- **Intel gets its own namespace.** Every `torch.xpu` call is wrapped so a build without the capability returns `False` or `0` instead of raising. `hasattr` alone was not enough: on a CUDA-only build `torch.xpu.synchronize()` raises `AssertionError`.
- **The startup VRAM patch no longer fails on a non-NVIDIA build.** It reports the backend it detected and why it skipped, instead of reading NVML and crashing.
- **ComfyUI's own flags are authoritative.** `is_intel_xpu()` / `is_amd()` already require `cpu_state == GPU`, and `get_torch_device()` tests XPU before CUDA, so the probes mirror that order rather than inventing a CUDA-first rule.

## 6. Verification performed

Measured on this machine (RTX 5060 Ti, torch 2.15.0+cu134, CUDA 13.4):

```
is_nvidia_build   : True
is_amd            : False
is_xpu            : False
host_pin_supported: True
xpu_device_count  : 0
capability_report : {'is_xpu': False, 'is_amd': False, 'is_nvidia_build': True,
                     'xpu_is_available': False, 'xpu_device_count': 0,
                     'hip': None, 'cuda': '13.4', 'host_pin_supported': True}
```

- `torch.version.hip` is `None` and `torch.xpu.is_available()` is `False` here, which is why the XPU and ROCm arms cannot be exercised on this machine.
- The module imports nothing from ComfyUI at import time; `comfy.model_management` is imported lazily inside the probes, so a CUDA run pays no import cost and cannot be affected by importing it.
- Retro-measured call-site counts after the change: `_db.*` 24 in `nodes/purge_vram.py`, 17 in `nodes/memory_manager.py`; `torch.cuda.*` unchanged at 41 and 15.

## 7. Limits

- **Not verified on AMD or Intel hardware.** No such GPU is available here, so no XPU or ROCm device has executed a single line of these arms. What is measured is the branch decision on a CUDA build and the shape of the calls.
- `torch.xpu` API names are used as documented by PyTorch; they have not been executed against a real XPU device.
- The ROCm arm relies on ROCm publishing through `torch.cuda`. That is a property of ROCm builds, not something this change can test here.
- Amount of memory actually reclaimed on either backend is unmeasured.

## 8. Constraints kept

- No change to the CUDA call sites, to Method 2c, to Method 2d, or to the ordering of the per-family purges.
- No new node input and no new toggle.
- No absolute path and no environment-specific value in the code.
- Root and `nodes/` copies of both nodes are byte-identical, as the package requires.
- Nothing from ComfyUI is imported at module import time.
