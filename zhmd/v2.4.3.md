## 1. 错误内容

### 1.1 观察到的顺序

1. 首次使用 SDXL HSWQ **NVFP4**（ConvRot / kitchen `quantize_nvfp4` 路径）提示词：**成功**。
2. DistOrch **Purge VRAM V2** 在启用 **HSWQ** 开关下运行（历史上日志前缀为 `HSWQ INT8:`）。
3. 在**同一** ComfyUI 进程中第二次提示词：forward 被 kitchen / TC pooled 路径失败刷屏。

### 1.2 代表性异常（第二次运行）

```text
pooled TC path failed: quantize_nvfp4() ... Invoked with types: PyCapsule ...
```

典型形态：

- 异常类：`TypeError`（或包装日志 `pooled TC path failed`）
- 内核 / 绑定：`comfy_kitchen` CUDA 扩展 `quantize_nvfp4`
- 意外参数类型：**`PyCapsule`**（DLPack / 已死 tensor storage 句柄），而期望的是存活的 CUDA tensor 缓冲区
- 时机：在 DistOrch HSWQ purge 各方法**之后**（尤其是核爆式 CUDA tensor 销毁 + 此前仅清理 kitchen 字典的 Method 2c）

### 1.3 首次运行日志长什么样（健康）

健康的首次运行通常可见：

- NVFP4 栈已应用（`full stack applied` / LoRA bake OK）
- 无 `pooled TC path failed`
- `quantize_nvfp4` 参数类型中无 `PyCapsule`

### 1.4 本修复前 DistOrch 的日志（相关摘录）

Method 2c 已运行，但只报告了 kitchen 侧的 bag，例如：

```text
HSWQ INT8: Method 2c - Reset comfy_kitchen CUDA caches...
HSWQ INT8: Reset comfy_kitchen CUDA caches _cublas_workspaces=..., _empty_cuda_tensors=...
```

**缺失**（修复前）：类似如下的任何一行：

```text
Cleared HSWQ NVFP4 runtime pools / CUDA graphs
... nvfp4_runtime_pools ...
```

这一缺失就是 DistOrch 侧的铁证：kitchen 缓存已重置；**NVFP4 模块级池并未清理**。

### 1.5 相关的 INT8 历史错误（同一 Method 2c 家族）

INT8 在 purge 后的第二次生成，此前在 kitchen cuBLAS workspace 上以类似模式失败：

```text
cublas_gemm_int8 ... PyCapsule ...
```

Method 2c 已为该 INT8 情况清理 `_cublas_workspaces` / `_empty_cuda_tensors`。NVFP4 失败属于**同一结构类别**，但池所有者是**另一个**（`nvfp4_runtime`）。

## 2. 根因

### 2.1 DistOrch HSWQ purge 会激进销毁 CUDA storage

当 HSWQ purge 开关打开时，DistOrch 会走若干方法，包括：

| Method | 作用 |
|--------|------|
| Method 0 / 0s | PinCache / Detailer SEGS / PromptExecutor 缓存 |
| Method 1 | `unload_all_models` / `free_memory` |
| Method 2 / 2b | 强制注销 ComfyUI `PINNED_MEMORY` |
| Method 3 | 核爆式 `gc` 扫描 — 替换 / 销毁大型 CUDA tensor storage |
| Method 2c | 重置仍持有死引用的**模块级** CUDA 缓存 |

Method 0s / Method 3 并不只是释放“模型”。它们遍历存活的 Python 对象（`gc.get_objects()` / SEGS 扫描），并对仍被缓存引用的大型 tensor **替换或清空 CUDA storage**。

### 2.2 HSWQ NVFP4 在这些 dict 之外保有模块级池

在 ComfyUI-nunchaku-unofficial-loader 中，NVFP4 激活 / 旋转 / CUDA-graph 复用位于：

`nodes/nvfp4/nvfp4_runtime.py`

概念上：

| 符号 | 作用 |
|--------|------|
| `_ACT_Q_POOL` | 为 `quantize_nvfp4_act_pooled` 复用的 `qx` / scale 缓冲区 |
| `_ROT_OUT_POOL` | 复用的 rotate matmul 输出 |
| `_GRAPH_CACHE` | NVFP4 GEMM 路径的 CUDA graphs |
| `clear_nvfp4_runtime_pools()` | 清理以上全部 |

这些池是**模块全局变量**。DistOrch Method 3 可能：

1. 通过 `gc` 找到池**内部的 tensor**，并
2. 销毁 / 替换其 CUDA storage，

而**dict 条目仍然保留**，仍指向底层 storage 已失效的 Python tensor 对象。

### 2.3 为何仅靠 reload 无法自愈

purge 之后：

- UNet / MODEL 可能已卸载并稍后重新加载。
- 重新加载**权重**并**不会**重建 `_ACT_Q_POOL` / `_ROT_OUT_POOL` / `_GRAPH_CACHE`。
- 下一次 forward 仍会调用 `quantize_nvfp4_act_pooled` → kitchen `_C.quantize_nvfp4(...)`。
- Kitchen 为 DLPack 包装缓冲区；死 storage 在绑定时表现为 **`PyCapsule`** → `TypeError`。

### 2.4 为何 INT8 清理已存在，NVFP4 仍会坏掉

Method 2c 已清理 **comfy_kitchen** 模块 dict：

- `_cublas_workspaces`
- `_empty_cuda_tensors`

这对 INT8 `cublas_gemm_int8` 的 PyCapsule 类已足够。

NVFP4 池位于**另一个包**（`nvfp4_runtime`），不在 `comfy_kitchen.backends.cuda`。只清 kitchen 会留下中毒的 NVFP4 池。

### 2.5 次要导入陷阱（为何安装看起来“没修好”）

本仓库有两套 purge 实现：

| 路径 | 作用 |
|------|------|
| `nodes/purge_vram.py` | 规范实现（Method 2c + NVFP4 清理） |
| 根目录 `purge_vram.py` | 遗留副本；可能落后于 `nodes/` |

若 `__init__.py` **优先导入根目录**，ComfyUI 会继续执行旧的 Method 2c（仅 kitchen）。优先 `.nodes.purge_vram` 是为了让用户更新自定义节点后，DistOrch 侧的 NVFP4 清理真正跑起来。

## 3. 对策概览

### 3.1 DistOrch 侧策略（本说明）

1. **保留**现有 INT8 / kitchen Method 2c 行为。
2. **增加**对 `sys.modules` 中任意已加载 `nvfp4_runtime` 模块调用 `clear_nvfp4_runtime_pools()`（导入名随 ComfyUI 自定义节点布局而变）。
3. **优先**从 `.nodes.purge_vram` 导入 `DisTorchPurgeVRAMV2`，避免过时的根目录 `purge_vram.py` 静默胜出。
4. 将日志前缀从 `HSWQ INT8:` **改为** `HSWQ INT8/NVFP4:`，使 purge 日志与 INT8+NVFP4 双重 Method 2c 范围一致。

### 3.2 DistOrch 日志中的成功形态

在加载了修复后的 `nodes/purge_vram.py` 并重启 ComfyUI 之后：

```text
HSWQ INT8/NVFP4: Method 2c - Reset comfy_kitchen CUDA caches...
HSWQ INT8/NVFP4: Cleared HSWQ NVFP4 runtime pools / CUDA graphs
HSWQ INT8/NVFP4: Reset comfy_kitchen CUDA caches ..., nvfp4_runtime_pools
```

（具体 kitchen bag 名称可能变化；关键新增标记是 `nvfp4_runtime_pools` 和/或 “Cleared HSWQ NVFP4 runtime pools” 行。）

然后：第一次提示词 → purge → 第二次提示词必须对 `quantize_nvfp4` 显示**零**次 `pooled TC path failed` / `PyCapsule`。

### 3.3 本 DistOrch 修复*不*声称的内容

- 它不替代 loader 侧 early-return / upgrade 时的池清理（那是 unofficial-loader 中的另一道安全网）。
- 它不删除 Nunchaku SVDQ 路径。
- 除日志标注与 Method 2c 的 NVFP4 增补外，它不改变 INT8 PinCache / SEGS / Method 3 算法。

### 3.4 本仓库中修复所在位置

| 文件 | 对本修复的作用 |
|------|-------------------|
| `nodes/purge_vram.py` | 规范 Method 2c 正文（kitchen + NVFP4 池清理） |
| `__init__.py` | 优先从 `.nodes.purge_vram` 导入 `DisTorchPurgeVRAMV2` |
| `purge_vram.py`（仓库根目录） | 仅遗留回退；可能不含 NVFP4 清理 |

用户通过从本仓库更新 **ComfyUI-DistorchMemoryManager**（Manager / git pull / release 包）获得修复，然后完全重启 ComfyUI，以便加载新的 `nodes/purge_vram.py`。

## 5. 新增 / 修改的 DistOrch 代码全文

### 5.1 `__init__.py` — Purge VRAM V2 导入优先级

```python
# Import Purge VRAM V2 node.
# Prefer nodes.purge_vram (Method 2c clears HSWQ NVFP4 runtime pools after DistOrch
# nuclear kill). Root purge_vram.py is legacy fallback only.
try:
    from .nodes.purge_vram import DisTorchPurgeVRAMV2
    print("[ComfyUI-VRAM-Manager] Successfully imported DisTorchPurgeVRAMV2 from .nodes.purge_vram")
except ImportError as e:
    try:
        from .purge_vram import DisTorchPurgeVRAMV2
        print("[ComfyUI-VRAM-Manager] Successfully imported DisTorchPurgeVRAMV2 from .purge_vram")
    except ImportError as e2:
        print(f"[ComfyUI-VRAM-Manager] WARNING: Failed to import DisTorchPurgeVRAMV2: {e2}")
        DisTorchPurgeVRAMV2 = None
```

### 5.2 `nodes/purge_vram.py` — `_reset_comfy_kitchen_cuda_caches`（Method 2c 正文）

这是随 INT8 kitchen + NVFP4 池清理一并交付的完整嵌套函数（含日志前缀）：

```python
                def _reset_comfy_kitchen_cuda_caches() -> None:
                    """Drop comfy_kitchen + HSWQ NVFP4 pooled CUDA buffers after nuclear kill.

                    Method 0s / Method 3 walk gc.get_objects() and replace storage on
                    large CUDA tensors. That includes:

                    - comfy_kitchen cuBLAS workspace (``_cublas_workspaces``) →
                      dead tensor → ``cublas_gemm_int8`` PyCapsule (INT8 2nd gen)
                    - HSWQ NVFP4 ``_ACT_Q_POOL`` / ``_ROT_OUT_POOL`` / CUDA-graph
                      cache → dead qx/sx buffers → ``quantize_nvfp4`` PyCapsule
                      (ConvRot NVFP4 2nd gen after DistOrch purge)

                    Model reload alone does not recreate those module-level pools.
                    """
                    try:
                        import comfy_kitchen.backends.cuda as ck_cuda
                    except Exception as e:
                        print(f"HSWQ INT8/NVFP4: comfy_kitchen cuda import skipped: {e}")
                        ck_cuda = None
                    cleared = []
                    if ck_cuda is not None:
                        for attr in (
                            "_cublas_workspaces",
                            "_empty_cuda_tensors",
                        ):
                            bag = getattr(ck_cuda, attr, None)
                            if isinstance(bag, dict) and bag:
                                n = len(bag)
                                bag.clear()
                                cleared.append(f"{attr}={n}")
                    # HSWQ NVFP4 act / GEMM pools — scan sys.modules (import path varies).
                    for name, mod in list(__import__("sys").modules.items()):
                        if mod is None:
                            continue
                        if not (
                            name.endswith("nvfp4_runtime")
                            or ".nvfp4_runtime" in name
                        ):
                            continue
                        fn = getattr(mod, "clear_nvfp4_runtime_pools", None)
                        if not callable(fn):
                            continue
                        try:
                            fn()
                            cleared.append("nvfp4_runtime_pools")
                            print(
                                "HSWQ INT8/NVFP4: Cleared HSWQ NVFP4 runtime pools / CUDA graphs"
                            )
                            break
                        except Exception as e2:
                            print(
                                f"HSWQ INT8/NVFP4: NVFP4 runtime pool clear failed ({name}): {e2}"
                            )
                    if cleared:
                        print(
                            "HSWQ INT8/NVFP4: Reset comfy_kitchen CUDA caches "
                            + ", ".join(cleared)
                        )
                    else:
                        print("HSWQ INT8/NVFP4: comfy_kitchen CUDA caches already empty")
```

### 5.3 `nodes/purge_vram.py` — Method 2c 调用点（HSWQ purge 序列）

```python
                # Nuclear CUDA tensor kill may have destroyed kitchen workspaces
                # while leaving dead refs in module-level dicts — clear them.
                print("HSWQ INT8/NVFP4: Method 2c - Reset comfy_kitchen CUDA caches...")
                _reset_comfy_kitchen_cuda_caches()
```

### 5.4 日志前缀变更（同一文件）

此前使用前缀 `HSWQ INT8:` 的所有 HSWQ purge `print` 行现为：

```text
HSWQ INT8/NVFP4:
```

理由：Method 2c（以及 HSWQ purge 开关）同时覆盖 **INT8 kitchen workspace 清理** 与 **NVFP4 运行时池清理**。当同一路径也清理 NVFP4 池时，日志只写 `INT8` 会产生误导。

## 6. 代码含义

### 6.1 为何需要 Method 2c

Method 0s / 3 是**storage 杀手**。它们适合释放 SEGS / executor 缓存 / 游离 CUDA tensor 占用的 VRAM。若模块级 dict 在 storage 死亡后仍保留指向那些 tensor 的名字，则它们是**不正确**的。

Method 2c 是**字典卫生**步骤：

- 清理 INT8 GEMM 复用的 kitchen workspace。
- 清理 NVFP4 act quant / GEMM 复用的 NVFP4 池/graphs。

没有 Method 2c 时，“purge 成功”（已分配 VRAM 下降）仍可能给下一次 forward 留下**中毒缓存**。

### 6.2 Kitchen 清理块（`_cublas_workspaces`、`_empty_cuda_tensors`）

```python
for attr in ("_cublas_workspaces", "_empty_cuda_tensors"):
    bag = getattr(ck_cuda, attr, None)
    if isinstance(bag, dict) and bag:
        bag.clear()
```

**含义：**

- 这些 dict 为 comfy_kitchen 性能缓存 CUDA tensor。
- 核爆销毁后，条目可能已死。
- `.clear()` 丢弃引用，使下一次 INT8 kitchen 调用分配新缓冲区。
- 这是历史上的 INT8 第二次生成修复；**角色保持不变**。

### 6.3 NVFP4 `sys.modules` 扫描

```python
for name, mod in list(__import__("sys").modules.items()):
    if name.endswith("nvfp4_runtime") or ".nvfp4_runtime" in name:
        fn = getattr(mod, "clear_nvfp4_runtime_pools", None)
        if callable(fn):
            fn()
            ...
            break
```

**含义：**

- DistOrch 不得硬依赖某一个冻结导入字符串（`nodes.nvfp4.nvfp4_runtime` vs ComfyUI 可能注册的其他包限定名）。
- 扫描 `sys.modules` 可找到 unofficial-loader 实际导入时使用的名字。
- 调用 `clear_nvfp4_runtime_pools()` 清空 `_ACT_Q_POOL`、`_ROT_OUT_POOL` 与 CUDA graphs。
- 首次成功后 `break`：清理一次即可；避免双重清理噪声。

**若本会话从未导入 loader：** 无匹配模块 → cleared 列表中无 `nvfp4_runtime_pools`。这是正确的（无物可清）。NVFP4 跑过后模块应已存在。

### 6.4 为何 DistOrch 调用 loader API 而非复制池

池由 unofficial-loader 拥有。DistOrch 不应重实现池键。约定是：

1. Loader 导出 `clear_nvfp4_runtime_pools()`。
2. DistOrch Method 2c 在核爆销毁后调用它。
3. 下一次 NVFP4 forward 按需用存活 storage 重建池。

### 6.5 `__init__.py` 导入优先级 — 含义

```python
from .nodes.purge_vram import DisTorchPurgeVRAMV2  # first
# root purge_vram only if nodes import fails
```

**含义：**

- 运行时真相是 `nodes/purge_vram.py`。
- 根目录 `purge_vram.py` 可能漂移（较旧的、无 NVFP4 清理的 Method 2c、换行 churn、部分更新）。
- 优先 nodes 使 “`nodes/` 中 Method 2c 已更新” 等于 “ComfyUI 实际运行该 Method 2c”。
- 启动日志必须显示：

```text
Successfully imported DisTorchPurgeVRAMV2 from .nodes.purge_vram
```

若显示 `.purge_vram`（根目录），则安装落在遗留导入路径 — 在 `nodes/purge_vram.py` 成功导入前，NVFP4 清理可能缺失。

### 6.6 日志前缀 `HSWQ INT8/NVFP4:` — 含义

- UI 开关仍可能标为 `HSWQ`（遗留工作流接受 `HSWQ INT8`）。
- 控制台前缀标明该 purge 路径处理 **INT8 kitchen + NVFP4 池**。
- 排查第二次生成问题的操作者应搜索 `HSWQ INT8/NVFP4` 与 `nvfp4_runtime_pools`。

### 6.7 因果链（精简）

```text
Run 1 NVFP4
  → fills _ACT_Q_POOL / graphs with live CUDA tensors
DistOrch HSWQ purge Method 0s/3
  → destroys CUDA storage of those tensors (VRAM freed)
Method 2c kitchen-only (old)
  → kitchen dicts cleared; NVFP4 pools STILL hold dead tensors
Run 2 NVFP4
  → quantize_nvfp4 sees PyCapsule / TypeError
Method 2c + clear_nvfp4_runtime_pools (new)
  → pools empty; Run 2 allocates fresh buffers → OK
```

### 6.8 验证清单

1. 将 **ComfyUI-DistorchMemoryManager** 更新到包含本 Method 2c 变更的构建后，完全重启 ComfyUI。
2. 启动：从 `.nodes.purge_vram` 导入。
3. 运行一次 NVFP4。
4. 运行 DistOrch HSWQ purge；确认 Method 2c 日志出现 `nvfp4_runtime_pools` / “Cleared HSWQ NVFP4…”。
5. 第二次 NVFP4 提示词：无 `pooled TC path failed`，`quantize_nvfp4` 上无 `PyCapsule`。
