## 1. 问题所在

两个节点都按 CUDA 命名空间编写，且无条件调用。在 `850986b^` 上实测：

| 文件 | `torch.cuda.*` 调用点 |
| :--- | ---: |
| `nodes/purge_vram.py` | 41 |
| `nodes/memory_manager.py` | 15 |

在 AMD 构建上这些调用能到达 ROCm 运行时，因为 ROCm 通过 `torch.cuda` 暴露自身（`torch.version.hip` 有值、`torch.version.cuda` 为 `None`）。在 Intel 构建上则不行：设备是 XPU，`torch.cuda` 背后没有设备，分配器调用没有作用对象。启动时的显存补丁形态相同：它读取 NVML，而 NVML 只存在于 NVIDIA。

对应 [Issue #4](https://github.com/ussoewwin/ComfyUI-DistorchMemoryManager/issues/4)。

## 2. 根本原因

不存在后端判定。节点直接假定了它被编写时所在平台的设备命名空间与内存 API，因此每一个破坏性步骤都按 CUDA 表达，与 ComfyUI 实际运行在什么设备上无关。ComfyUI 本身早已区分这三种情况（`is_intel_xpu()` / `is_amd()` 都要求 `cpu_state == GPU`），且 `get_torch_device()` 先测 XPU 再退回 CUDA，但节点从未查阅这些标志。

## 4. 代码全文

### 4.1 后端探测（`nodes/device_backend.py`，76-107 行）

```python
def is_xpu():
    """True when ComfyUI runs on an Intel XPU.

    Returns False on this CUDA build by execution, which is the direct evidence
    that the CUDA path is untouched.
    """
    global _XPU_CACHE
    if _XPU_CACHE is not None:
        return _XPU_CACHE
    mm = _comfy_model_management()
    if mm is not None and hasattr(mm, "is_intel_xpu"):
        try:
            value = bool(mm.is_intel_xpu())
        except Exception:
            value = False
        _XPU_CACHE = value
        return value
    if not hasattr(torch, "xpu"):
        return False
    try:
        return bool(torch.xpu.is_available())
    except Exception:
        return False


def xpu_device_count():
    if not is_xpu():
        return 0
    try:
        return int(torch.xpu.device_count())
    except Exception:
        return 0
```

### 4.2 逐设备释放 XPU 缓存（176-205 行）

```python
def xpu_clear_cache_all_devices():
    """Synchronise then empty the XPU allocator on every device.

    Returns the number of devices whose cache was actually emptied. A build that
    cannot synchronise is reported once instead of being counted as success.
    """
    if not is_xpu():
        return 0
    cleared = 0
    sync_failures = 0
    try:
        current = xpu_current_device()
    except Exception:
        current = 0
    for index in range(xpu_device_count()):
        if not xpu_set_device(index):
            continue
        try:
            if not xpu_synchronize():
                sync_failures += 1
            if xpu_empty_cache():
                cleared += 1
        finally:
            xpu_set_device(current)
    if sync_failures:
        print(
            "Backend: XPU synchronize unavailable on %d device(s); "
            "the cache was emptied without waiting for in-flight work" % sync_failures
        )
    return cleared
```

## 5. 这意味着什么

- **CUDA 路径未改动。** `nodes/purge_vram.py` 中 `torch.cuda.*` 仍为 41 处，`nodes/memory_manager.py` 中仍为 15 处，与变更前一致。XPU 分支是在这些代码块之前加入的门控，不是替换。
- **AMD 继续使用 CUDA 命名空间。** ROCm 通过 `torch.cuda` 暴露自身，因此 ROCm 分支不需要新的命名空间，只需要正确的分支判定。
- **Intel 使用自己的命名空间。** 每个 `torch.xpu` 调用都被包装，能力缺失时返回 `False` 或 `0` 而不抛异常。仅用 `hasattr` 不够：在纯 CUDA 构建上 `torch.xpu.synchronize()` 会抛 `AssertionError`。
- **启动显存补丁在非 NVIDIA 构建上不再失败。** 它会报告检测到的后端以及跳过原因，而不是读取 NVML 后崩溃。
- **以 ComfyUI 自身的标志为准。** `is_intel_xpu()` / `is_amd()` 已要求 `cpu_state == GPU`，且 `get_torch_device()` 先测 XPU 再测 CUDA，因此探测沿用该顺序，不自造 CUDA 优先规则。

## 6. 已执行的验证

在本机实测（RTX 5060 Ti、torch 2.15.0+cu134、CUDA 13.4）：

```
is_nvidia_build   : True
is_amd            : False
is_xpu            : False
host_pin_supported: True
xpu_device_count  : 0
capability_report : {'is_xpu': False, 'is_amd': False, 'is_nvidia_build': True,
                     'xpu_is_available': False, 'xpu_device_count': 0,
                     'hip': None, 'cuda': '13.4', 'host_pin_supported': True}
```

- 本机 `torch.version.hip` 为 `None`、`torch.xpu.is_available()` 为 `False`，因此 XPU 与 ROCm 分支在本机无法被执行。
- 模块在导入时不导入 ComfyUI 的任何内容；`comfy.model_management` 在探测函数内部惰性导入，因此 CUDA 运行不承担导入成本，也不会因导入本模块而受影响。
- 变更后实测调用点数量：`nodes/purge_vram.py` 中 `_db.*` 24 处、`nodes/memory_manager.py` 中 17 处；`torch.cuda.*` 保持 41 处与 15 处不变。

## 7. 局限

- **未在 AMD 或 Intel 硬件上验证。** 此处没有这类 GPU，因此没有任何 XPU 或 ROCm 设备执行过这些分支的任何一行。已实测的是 CUDA 构建上的分支判定与调用的形状。
- `torch.xpu` 的 API 名称按 PyTorch 文档使用，但未在真实 XPU 设备上执行过。
- ROCm 分支依赖 ROCm 通过 `torch.cuda` 暴露自身。这是 ROCm 构建的性质，本次变更无法在本机检验。
- 两种后端上实际回收的内存量均未测定。

## 8. 保持的约束

- 未改动 CUDA 调用点、Method 2c、Method 2d，以及各家族清理的执行顺序。
- 未新增节点输入，未新增开关。
- 代码中不含绝对路径与环境特定值。
- 两个节点的根目录副本与 `nodes/` 副本逐字节相同，符合软件包要求。
- 模块导入时不从 ComfyUI 导入任何内容。
