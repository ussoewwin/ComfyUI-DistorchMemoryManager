## 1. 背景与重构动因

在以往版本中，为应对 ModelPatchLoader（如 Z-Image ControlNet、QwenImage BlockWise ControlNet、SigLIP MultiFeat Proj 等）在生成后残留补丁权重导致放大（Upscaling）阶段发生 OOM 的问题，本仓库提供了独立的 `Model Patch Memory Cleaner` 节点。

然而，在实际工作流构建中：
- 用户通常已在流程中放置了主力显存清理节点 `General Purge VRAM V2`（`DisTorchPurgeVRAMV2`）。
- 同时保留两个功能重叠的清理节点造成了节点面板臃肿和工作流布线冗余。
- 原 V2 节点虽然配备了 `clear_model_patches` 开关，但卸载逻辑之后缺少原单体节点的即时 `torch.cuda.empty_cache()` 和 `synchronize()` 调用，导致在保留主模型（`purge_models=False`）时无法立即将物理显存释放给系统。

---

## 2. 技术本质：补齐即时物理解放能力

在 `v2.4.9` 中，对 `nodes/purge_vram.py` 及根目录 `purge_vram.py` 的 `clear_model_patches` 执行分支进行了完全对齐与增强：

1. **补丁检测与安全剥离**：
   从 `current_loaded_models` 逆序扫描带有 `additional_models` 或 `attachments` 的 `ModelPatcher` 实例，将 `currently_used` 置为 `False` 并调用 `model_unload()` 卸载，同时从列表中弹出。
2. **垃圾回收**：
   调用 `comfy.model_management.cleanup_models_gc()`。
3. **即时物理显存回收**：
   在补丁卸载代码块内直接执行：
   ```python
   if torch.cuda.is_available():
       torch.cuda.empty_cache()
       torch.cuda.synchronize()
       print("GPU memory cleared")

   gc.collect()
   print("Garbage collection completed")

   print("Model patch memory cleanup completed")
   ```
这确保了即使用户将 `purge_models` 设为 `False`（保留基础 Diffusion/UNet 模型），被卸载的补丁显存也会在当前节点执行完毕的瞬间物理归还给显卡，100% 具备原单体节点的清理效能。

---

## 3. 节点注销与注册精简

在 `__init__.py` 中，已从 `NODE_CLASS_MAPPINGS` 和 `NODE_DISPLAY_NAME_MAPPINGS` 中正式注销 `ModelPatchMemoryCleaner`：
- ComfyUI 节点搜索面板现在只保留 3 类核心节点：
  - `General Purge VRAM V2`（`DisTorchPurgeVRAMV2`）
  - `Memory Manager (Advanced)`（`MemoryManager`）
  - `Patch Sage Attention DM`（`PatchSageAttentionDM`）
- 节点注册更加整洁规范，避免了多节点并存的混淆。

---

## 4. 迁移指引与推荐工作流

- **原工作流**：
  ```
  [ModelPatchLoader] → [ControlNet 节点] → [Model Patch Memory Cleaner] → [放大节点]
  ```
- **推荐工作流（v2.4.9 起）**：
  ```
  [ModelPatchLoader] → [ControlNet 节点] → [General Purge VRAM V2 (clear_model_patches=True)] → [放大节点]
  ```
  *(若希望保留 Diffusion 基础模型仅清理补丁，可将 `clear_model_patches` 保持为 `True`，并将 `purge_models` 设为 `False`)*。
