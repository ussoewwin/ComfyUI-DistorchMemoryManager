## 概述

**v2.4.4** 强化 **软清理**（HSWQ 开关 **关闭**）下的显存回收：MultiGPU Dynamic / NVFP4（如 Krea2）在 `model_unload()==True` 后不再残留约 **9–12 GB** CUDA；同时在邻近 Ollama 的 purge 后保留 **CPU CLIP / 文本编码器** 的重载源。此外在 v2.4.3 之后扩展 **HSWQ** Method **2c** / 核爆路径（完整 INT8/NVFP4/Detailer 残留清理、Z Image ConvRot parity / bake 剥离、Hadamard / inplace 池）。在另行下达升版命令前，Comfy Registry / `pyproject.toml` 包版本仍为 **2.4.3**；本标签记录 tip `6190024`（含 `zhmd/v2.4.4.md`）。

## 1. 软路径 — MultiGPU / NVFP4 CUDA 残留（HSWQ 关闭）

### 1.1 现象 A

1. 加载 / 运行大型 MultiGPU Dynamic 或 HSWQ **NVFP4**（Krea2 级）。
2. 运行 **DisTorch Purge VRAM V2**，**不勾选 HSWQ**（仅软路径）。
3. `model_unload()` 可能返回成功，但 **NVIDIA-SMI / Comfy 仍显示约 9–12 GB** 挂在残留 CUDA param/buffer 上。
4. 下次加载 OOM 或卡住，因为软清理从未真正请求释放。

### 1.2 根因

ComfyUI 的 `free_memory(0, device)` 对回收基本是 **空操作**。软 unload 后 `nn.Parameter` / buffer 上仍留有 CUDA `.data`。Memory Manager / Safe Memory Manager 此前同样调用 `free_memory(0, ...)`。

### 1.3 对策

软清理（`purge_models` / 激进 unload）时：

1. 标记 unused → `partially_unload` / `model_unload`。
2. 解包到 `nn.Module` → **仅强制清空残留 CUDA storage**（`_force_empty_cuda_storage`）。
3. 从 `current_loaded_models` 弹出 → `cleanup_models()`。
4. `unload_all_models()` + 对每个 `cuda:i` 调用 **`free_memory(1e30)`**。
5. 可选 `soft_empty_cache()`。

开启 `reset_virtual_memory` 时，**Memory Manager** / **Safe Memory Manager** 使用同样的 `1e30` 请求。

### 1.4 软路径摘录（`nodes/purge_vram.py` / 根目录 `purge_vram.py`）

```python
def _force_empty_cuda_storage(t) -> int:
    # NVFP4 / MultiGPU Dynamic: free leftover CUDA only.
    # Never wipe CPU tensors — after model_unload() they are
    # ComfyUI's reload source. Wiping to empty(0) made CLIP
    # Embedding.weight non-2D (Ollama purge → CLIPTextEncode
    # RuntimeError: 'weight' must be 2-D; reload logged 0.00 MB).
    ...
    if not is_cuda:
        return 0
    dtype = getattr(data, "dtype", torch.float32)
    empty = torch.empty(0, dtype=dtype, device="cpu")
    if hasattr(t, "data"):
        t.data = empty
    ...

# Hard free: unload_all + free_memory(1e30). free_memory(0) does nothing.
mm.unload_all_models()
for di in range(torch.cuda.device_count()):
    mm.free_memory(1e30, torch.device(f"cuda:{di}"))
```

### 1.5 Memory Manager 摘录（`memory_manager.py`）

```python
# free_memory(0, ...) is a no-op and left Krea2 NVFP4 ~9GB resident.
for di in range(torch.cuda.device_count()):
    comfy.model_management.free_memory(1e30, torch.device(f"cuda:{di}"))
```

### 1.6 期望的软路径日志

```text
Unloaded N model(s)
Force-killed ~X.XX GB CUDA storage from loaded models (MultiGPU/NVFP4 soft-unload residue)
unload_all_models() issued
free_memory(1e30) issued for all CUDA devices
```

## 2. 软路径 / HSWQ 核爆 — 仅 CUDA 的 `empty(0)`（保护 CLIP / TE）

### 2.1 现象 B

1. 在也涉及 **Ollama** / 大型 TE 的工作流后做软清理或 HSWQ purge。
2. 下一次 **CLIPTextEncode** / Z Image TE encode 失败：

```text
RuntimeError: 'weight' must be 2-D
```

3. 重载日志显示 CLIP / TE 为 **0.00 MB** — CPU embedding storage 被 `empty(0)` 清空。

### 2.2 根因

早期「杀掉所有残留 storage」的路径对 **CPU** tensor 也调用了 `torch.empty(0)`。`model_unload()` 之后 CPU 权重是 ComfyUI 的重载源；清空后留下非 2D 的 `Embedding.weight`。

### 2.3 对策

软路径 `_force_empty_cuda_storage` 与 HSWQ `_kill_tensor_storage` 均在 **`data` 非 CUDA 时直接返回**。仍可注销 pinned CUDA host memory；纯 CPU tensor 不动。

```python
def _kill_tensor_storage(t) -> int:
    # Same rule as _force_empty_cuda_storage: unpin/CPU-safe only;
    # empty(0) only for CUDA. CPU wipe broke ZI TE after Ollama purge.
    ...
    if not is_cuda:
        return 0
```

## 3. HSWQ 开启 — Method 2c / 核爆扩展（相对 v2.4.3）

v2.4.3 修复了 NVFP4 **运行时池**（`clear_nvfp4_runtime_pools` / 第二次生成的 `PyCapsule`）。v2.4.4 保留该修复，并补上 HSWQ purge 开启时仍会污染下一模型的表面。

### 3.1 现象 C — Z Image → SDXL / product-stack 污染

Z Image NVFP4 ConvRot / LoRA bake 之后，HSWQ purge 清理了 kitchen / 部分池，但 **parity / bake 钩子** 与 **INT8-protect 加载臂** 仍可能留在 `sys.modules` / `comfy.ops`。随后 SDXL 加载继承了 ZI TC product stack 或 `_hswq_int8_protect_*`（`Params.convrot=False` / 错误 VER bake）。

### 3.2 对策 — Method 2c 内剥离 API

扫描 `sys.modules` 中的 NVFP4 / Z Image 模块，若存在则调用：

| API | 作用 |
|-----|------|
| `_clear_zimage_parity_contamination_for_sdxl` | 在 SDXL 前清除 ZI parity 污染 |
| `restore_nvfp4_tc_product_stack` | 恢复产品 TC 栈 |
| `uninstall_zimage_nvfp4_lora_bake` | 移除 ZI LoRA bake 钩子 |

并剥离 `ops._load_quantized_module` 上的 ZI INT8-protect 包装（闭包单元 / PRODUCT wrap），避免 SDXL INT8 ConvRot 被错误再武装。

```text
HSWQ INT8/NVFP4: HSWQ stack peel restore_nvfp4_tc_product_stack via ... -> ...
HSWQ INT8/NVFP4: HSWQ stack peel uninstall_zimage_nvfp4_lora_bake via ... -> ...
```

### 3.3 现象 D — INT8 / Detailer / Hadamard / inplace 残留

HSWQ purge 后的第二次生成仍可能撞上：

- 超出 kitchen workspace 的完整 INT8 / NVFP4 模块袋
- Detailer / SEGS / PinCache 残留（Method 0 族）
- 跨提示词持有的 Hadamard / inplace CUDA 池

### 3.4 对策

Method **0–2c** 仍 **仅由开关门控**（HSWQ 关闭时不自动武装）。HSWQ 开启时，Method 2c / 核爆路径扩展清理：

- Kitchen `_cublas_workspaces` / `_empty_cuda_tensors`（既有）
- NVFP4 运行时池 / CUDA graphs（v2.4.3）
- 更广的 INT8/NVFP4/Detailer 残留字典与 Hadamard / inplace 池
- 上述 ZI 剥离 API

日志前缀仍为：`HSWQ INT8/NVFP4:`。
